## The crash: a pre-existing use-after-free, now fixed

The first pass ran all six batches at `--threads 4`. The
**treatment seat-B** batch died partway through:

```
$ ./build/riftbound --agent1 mcts:sims=20 --agent2 mcts:sims=20,eval=corpus \
    --deck1 decks/rengar_test.txt --deck2 decks/kennen_tyler.txt \
    --games 100 --threads 4 --seed 1000
  Progress: 46/100 games ...
terminate called after throwing an instance of 'std::runtime_error'
  what():  Battlefield not found: 37
Aborted   (exit 134)
```

### Root cause

Full analysis:
`.superpowers/sdd/2026-09-07-corpus-evaluator/crash-analysis.md`.
Summary — and it is **not** a data race, and **not** the corpus
evaluator's fault:

`GameState::battlefields` was a `std::vector<BattlefieldState>`, and
`GameEngine::setupBattlefields` built it with exactly two `push_back`s
and no `reserve` — so for the whole game `size() == capacity() == 2`,
and the next append was a **guaranteed reallocation**.
`EffectExecutor::addBattlefieldToken` does exactly that append, and its
one caller is Baron Nashor's "add the Baron Pit battlefield token to the
board". `1 Baron Nashor` is in `decks/kennen_tyler.txt`, which is in
every crashing batch. Three engine sites held a `BattlefieldState&`
**across card resolution** and then read and wrote it: the
staged-battlefield loop in `advanceMainPhase`, `runShowdown`, and
`runCombat`. The reallocation freed the buffer under those references.
`BattlefieldState::id` sits at offset 0, so a stale read returned
whatever now occupied those bytes — a heap pointer's low half
(`3691939024`), or a `GameObjectId` from a `std::vector<GameObjectId>`
that reused the chunk (`37`) — and that value went straight into
`getBattlefield`, which threw. The SIGSEGVs are the same defect on its
write side.

Why the corpus evaluator, and why threads:

- **The evaluator changes the game that gets played.** The corpus
  heuristic pays for battlefields controlled and for board width, so
  the bot contests battlefields and deploys units far more often, and
  reaches Baron plays (including inside every MCTS simulation) at a much
  higher rate.
- **The corpus evaluator is the first thing in the MCTS loop that
  allocates.** Freed memory that nothing reuses still holds its old
  bytes, so a stale `bf.id` reads back `0` or `1` and the game finishes
  as if nothing happened. `eval=score` was **surviving the same bug
  silently**, not avoiding it.
- **Thread count changes the allocator, not the logic.** `--threads 1`
  runs every game on the main thread in glibc's `brk`-backed main arena
  with stable LIFO reuse; `--threads N` gives each worker its own
  `mmap`-backed arena with different reuse order and the possibility of
  the region being released outright.

### The fix (Task 12a)

Both halves, belt and braces:

1. `GameState::battlefields` is now a **`std::deque<BattlefieldState>`**
   — appends never relocate existing elements, which makes all
   `getBattlefield` call sites and every range-`for` over `battlefields`
   correct by construction. Each use was checked: only `operator[]`,
   `push_back`, `size`, `back`, `front`, `empty` and range-`for` appear,
   with no `.data()`, no `reserve` and no contiguity assumption anywhere
   in `src/` or `tests/`.
2. The three sites no longer hold a reference across resolution. The
   staged-battlefield loop iterates a **snapshot of ids** and re-fetches
   before each read and each write; `runShowdown`, `runCombat`, and (for
   the same reason) `combatDamageStep` and `combatResolutionStep`
   re-fetch by id after every nested call that can resolve a card.
   `getBattlefield` now carries the lifetime contract as a comment.

Guarded by `tests/test_battlefield_stability.cpp`, which fails
deterministically on the pre-fix vector build.

deck on both sides, so deck strength and seat bias cancel and the only
difference is the evaluator.

Post-fix logs: `abfx-mirror-corpusP1.log`, `abfx-mirror-corpusP2.log`
(both `EXIT=0`, zero crashes at `--threads 4`).

**They agree exactly on win counts, so the verdict does not move**:
46.0% (92/200), Wilson 95% [39.2%, 52.9%].

Two things this comparison does and does not establish. It does show
that the pre-fix numbers were not corrupted in a way that changed who
won — the use-after-free was executing in those runs too, and it turns
out to have been benign there, which was suspected at the time but not
provable. It does **not** mean the fix is a no-op: the average decision
counts moved slightly (701 to 699, 697 to 696), which is exactly what
you would expect when writes like `bf.showdown_staged = false` and
`bf.combat_phase = ...` start landing on the live battlefield instead of
on freed memory. A handful of games take a marginally different path;
none of them changed hands at this sample.

## Verdict

**NOT DISTINGUISHABLE at this sample; point estimate slightly below.**

The mirror control puts the corpus evaluator at 46.0% (92/200) with a
95% interval of [39.2%, 52.9%]. That interval **includes 50%**, so by
the spec's rule the result is not distinguishable from the score
evaluator at this sample size. The point estimate is slightly below
50%, not above it. There is no evidence here that `eval=corpus` is
better, and none that it is meaningfully worse either — the sample
cannot separate them. Resolving an effect of this size at this variance
would take on the order of 800–1000 games per seat, not 100.

The treatment cell (40.0%, [33.5%, 46.9%]) sits 2.5pp below its
baseline (42.5%, [35.9%, 49.4%]) with heavily overlapping intervals —
also not a distinction, and confounded by a deck matchup that is
unfavourable before the evaluator is changed at all.

**Standing framing, which applies to every number above.** MCTS at
`sims=20` plays *legal* Riftbound, not *expert* Riftbound: twenty
simulations is far too few for the search to be the thing under test,
so the evaluator is steering something close to a random walk. And the
corpus evaluator plays *the book* — it encodes hand-written heuristics
and does not learn. Neither of these numbers says anything about what a
trained evaluator would do; they say what this hand-written one does at
this budget.
